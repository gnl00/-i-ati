## 结论与范围

最新「Ponte 低延迟原理分析」（chat `806`，22:32）为 204.937 秒、23 次工具调用、19 轮主模型、877,548 token。比 805 多出的 57.138 秒主要落在视觉/恢复分支：一次 60.009 秒视觉超时及后续 OCR、展示重试；首次 render 成功反馈反而提前到 72.053 秒。详见文末“再次复测”章节。

此前复测「Surge Ponte 低延迟原理对比」（chat `805`）为 147.799 秒、17 次工具调用、10 轮主模型、442,877 token；相对首次 ati 分别下降 52.5%、46.9%、54.5%、64.6%。相对已无视觉分析的上一轮，耗时基本持平、token 再降 26.4%。效率改善已可见，证据边界与图形内容仍需优化；完整口径和建议见文末“最新复测”章节。

首次基线的相同用户任务中，ati 耗时为 piagent 的 4.56 倍，主模型累计 token 为 6.12 倍，实际工具调用为 2.29 倍。两边的上下文、可用工具、skills、环境准备和检查步骤不同，这些数字代表本次执行路径的差异，不能直接解释为框架本身慢了多少。

ati 的额外检索和视觉检查带来更大的工作范围；同时，记录中也有可明确处理的损耗：两次相近的站点问答请求均失败，技能脚本不能按指定入口启动，图片分析使用了错误参数，以及图形修改多轮未消除同一种告警。建议先减少这些恢复与试探，再依据请求组成优化上下文，保持现有能力和交付质量。

初次调查交付为分析文档和优化建议。后续已批准并实现技能工具与检索/修改收口优化，见文末实施及复测记录；下一轮候选项继续保留为讨论范围。

## 调用差异与问题归类

### 工具数量只反映部分工作量

| 阶段 | ati 调用数 | ati 工具执行时长之和 | 主要行为 |
| --- | ---: | ---: | --- |
| 网页检索 | 10 | 22.635 秒 | 7 次 fetch、3 次 search |
| 技能与环境准备 | 9 | 0.146 秒 | 激活、4 次文档读取、脚本启动、配置、目录检查 |
| 图形制作 | 8 | 7.728 秒 | 2 次写入、1 次读取、4 次渲染、1 次导出 |
| 视觉检查与展示 | 3 | 44.541 秒 | 2 次分析、1 次图片展示 |
| 内部维护 | 2 | 0.011 秒 | 情绪报告、工作上下文更新 |

piagent 为 2 次 `read`、11 次 `bash` 和 1 次 `write`，其中包含两次网页读取、配置检查、参考文档读取、两次渲染和一次导出。一个 shell 调用可以组合多条命令，因此 32 对 14 不能解释为执行了 2.29 倍的底层操作。模型请求轮数和语义任务数量应一起看。

### 网页读取的问题是相近试探与失败收口

逐项复核后，ati 的 7 次 fetch 没有完全相同的 URL。5 次成功响应的正文哈希也各不相同。这份样本没有证明同一份成功网页正文被原样反复获取。

| 次序 | 读取目标 | 结果 | 评价 |
| --- | --- | --- | --- |
| 1 | Ponte 中文指引 | 成功 | 用户直接指定的主来源 |
| 2 | 知识库 `llms.txt` | 成功 | 用来发现相关文档，增加一次目录读取 |
| 3 | `index.md?ask=…&goal=…` | HTTP 500 | 站点问答接口失败 |
| 4 | `zh/technotes/nat-type.md` | 成功 | 为 NAT 条件补充独立依据 |
| 5 | `zh/guidelines/ponte.md?ask=…&goal=…` | HTTP 500 | 换页面追问同类问题，再次失败 |
| 6 | Surge Mac 6 发布说明 | 成功 | 引入版本变化和性能信息 |
| 7 | V2EX 讨论 `t/1093488` | 成功 | 为稳定性与使用体验补充社区材料 |

两次 `ask` 的执行时间合计约 9.447 秒，但其成本还包含中间决策、再次请求与结果进入后续上下文。直接扣除 9.447 秒会低估恢复成本，全部后续时间都算给失败又会高估。

两次相近尝试也不能证明所有第二次尝试都不合理。值得改进的是：第一次 HTTP 500 之后，模型没有可靠信息确认第二个端点能提供不同结果；此时已有可读取的普通文档，可以明确记录「没有找到协议细节」，转向现有证据完成回答。

三次搜索围绕延迟原理、中文协议解释和社区对比展开，彼此相关但目标并非完全一致。应判断每次搜索补上了哪个证据缺口，而非把相近关键词一律认定为重复。piagent 的中英文页面也有语义重叠，不能只对 ati 使用重复阅读的标准。

本次两边均未读取 Tailscale 官方正文。ati 增加了 Surge 文档和社区来源，但来源数量不能直接证明比较结论更可靠。后续验收要同时检查跨产品结论的来源覆盖、事实与推断的区分。

### 两次工具使用失败有明确入口

`run_skill_script` 直接启动 `.mjs` 文件，返回 `EACCES`，随后模型改用 `exec` 加 `node` 完成同一项配置检查。当前 [SkillToolsProcessor](../../../src/main/tools/skills/SkillToolsProcessor.ts) 对 `.ts` 选择 `bun`，其他扩展名按脚本自身可执行文件启动。这解释了为何专用入口失败而显式解释器调用成功。

这里还存在工作目录差异：专用技能入口固定在 skill root 执行，`exec` 的这次调用在聊天工作区执行。配置发现与输出位置会因此变化。优化时需要同时明确解释器和工作目录，不能只消除 `EACCES` 后就宣布与恢复路径等价。

第一次 `image_analyze` 使用顶层 `file`，实际契约支持 `files` 或 `images[].file`，返回缺少图片输入。第二次改为 `files` 后成功。当前 [视觉工具定义](../../../src/shared/tools/vision/definitions.ts) 已禁止额外顶层属性，但这次错误参数仍进入处理器；定义存在与运行链路有效校验需要分开验证。

本轮共识别 4 次工具业务失败，占 32 次调用的 12.5%：两次 HTTP 500、一次脚本启动失败、一次图片参数错误。部分外层工具段显示 `status: success`，实际返回对象是 `success: false`。失败统计应同时区分执行层状态、工具业务结果与结构化 failure，不能只看 UI 状态。piagent 的 14 条 toolResult 均为 `isError=false`，这不保证组合 shell 中每条子命令都成功。

### 图形迭代消耗了较多推理与往返

ati 的四次渲染依次为：初版出现端口拥挤告警；加长标签后告警仍在；改变行布局并移除部分连接后仍有同类告警；最终合并为三个通道后告警消失。piagent 初版也有布局告警，一次 patch 后收敛，共两次渲染。

修复真实布局问题属于有效工作。ati 暴露出的效率问题是连续修改没有消除同类告警，仍持续采用局部修补，随后才简化结构。建议在同类告警持续时检查修改是否作用于告警涉及的布局属性，或直接采用更简单的表达，减少无效修补。

本次 ati 推理 token 为 15,927，pi 为 2,527。ati 最终文字为 1,852 个 JavaScript 字符，pi 为 1,341 个，约相差 1.38 倍。字符不是 token，但这个差异足以说明输出 token 的 4.81 倍不能只归因于最终回答更长；还包括推理、工具参数和中间生成。

### 高缓存率仍然伴随较大输入成本

累计输入差异可以拆成：请求轮数约 1.83 倍，乘以每轮平均输入约 3.36 倍，得到约 6.16 倍。减少无效往返和减少每轮负担都有效。

ati 首轮输入已经比 pi 大 3.75 倍，后续又从 30,808 增到 73,448 token。这个事实支持核对提示词、工具 schema、技能目录、动态上下文和历史回放的占比；尚不能证明哪一项是主因，也不能证明存在重复拼接。

pi 的前置寒暄预热了缓存，本任务首轮缓存为 8,064 / 8,222；ati 首轮为 6,144 / 30,808。整体 94.42% 对 93.22% 不宜用于判断哪个框架缓存策略更优。即便 ati 总体命中率略高，未缓存输入仍是 pi 的 5.07 倍。

## 应复用的现有能力

采样时实现已有以下机制，优化不应重新增加一套同类系统：

- **Skills 按需加载。** [SkillsPromptProvider](../../../src/main/hosts/chat/preparation/request/SkillsPromptProvider.ts) 构建可用目录；[LoadedSkillsContextProvider](../../../src/main/hosts/chat/preparation/request/LoadedSkillsContextProvider.ts) 提供激活名称和路径。`load_skill` 再 `read_skill_file` 是现有设计，不能直接算作正文被重复注入。参见 [加载说明](../../integrations/skills-prompt-loading-optimization-summary.md)。
- **稳定的工具模型视图和文件恢复。** [ADR-0033](../../decisions/0033-stable-tool-result-model-content.md) 保留原始结果，生成有上限的稳定 `modelContent`；[ADR-0036](../../decisions/0036-runtime-context-manager.md) 由 ContextManager 管理整份请求预算。按轮次反复改写旧结果会影响证据稳定性和缓存前缀，若要改变，需要单独评估取舍。
- **搜索发现与正文读取分离。** [Web 工具说明](../../guides/development/web-search-and-fetch.md) 明确搜索只返回发现元数据。重新让搜索自动抓取全部结果，会增加本次已经暴露的检索成本。
- **有界网页并发。** [ADR-0044](../../decisions/0044-bounded-web-fetch-batch-concurrency.md) 已让连续、无需确认的 fetch 最多三个并发。本次部分 fetch 确实重叠执行。继续扩容窗口不能解决先后多轮的相近追问，还会增加资源占用。

## 建议的优化顺序

最小方案是先修正专用工具入口、补充准确调用示例，并让检索按证据缺口收口。它沿用已有工具与调度，不新增服务、账户或配置。完整方案再补请求组成观测，根据数据决定上下文优化范围。

| 优先级 | 候选项 | 预期收益 | 改动与风险 | 验收依据 |
| --- | --- | --- | --- | --- |
| P0 | 技能脚本的解释器与 cwd 契约 | 消除本例启动失败和模型恢复往返 | 范围小；改变 cwd 会影响配置和产物位置，须单独明确 | `.mjs` 无执行位仍能通过受支持解释器运行；路径、审批、取消与输出目录保持约定 |
| P0 | 视觉参数的有效校验与错误引导 | 消除顶层 `file` 这一类错误后的试探 | 优先准确示例及明确错误；避免为一个错误增加多套参数别名 | 合法 `files` 和 `images[].file` 均成功；错误输入明确指出有效形式；不调用提供商 |
| P0 | 业务失败的统一统计口径 | 识别被外层 success 掩盖的失败与恢复成本 | 优先基于现有事件分析，验证后再决定是否改变契约或 UI | 本例稳定识别 4 次失败，区分 HTTP、环境和参数原因，保持调用 ID 可追踪 |
| P1 | 检索收口与相似失败后的策略切换 | 减少低信息增量的搜索与追问 | 优先调整搜索 skill 与错误恢复提示；过早收口会漏证据 | 成功直读来源得到保留；相似接口持续失败时转读普通文档；跨产品关键断言仍有依据 |
| P1 | 图形同类告警后的收敛策略 | 减少无效 patch、推理和请求轮数 | 优先检查现有 skill 和错误反馈；简化结构须保留关键关系 | 同类告警重复时采用有依据的结构调整，最终无关键布局问题；同时记录交付质量 |
| P1 | 每轮请求组成与调用链用量归因 | 找出首轮与后续输入的主要贡献者 | 复用请求适配与事件边界，不复制运行状态；避免记录密钥和正文 | 每轮有系统提示、工具、目录、动态上下文、历史的体量归因；本地估算与提供商用量分列 |
| P2 | 重复读取的 run 内观测与复用 | 减少将来确认的相同来源网络读取 | 先观察，再做仅限当前 run 的精确键复用；保留查询、语言、版本、登录态语义 | 已完成的相同成功请求可复用；显式刷新仍读取；不同查询与失败结果不误合并 |
| P2 | 按任务缩减工具暴露与上下文 | 减少每轮输入和模型选择负担 | 范围较大，需先完成组成归因；可能降低工具可发现性 | 相同任务能力可达、关键事实可恢复，schema 与历史用量下降且质量不退化 |

检索策略的执行位置优先放在搜索 skill 和工具反馈。URL、查询和目标接近可以作为提示，不宜直接在 Dispatcher 中判断两个问题语义相同并强制禁止调用。当前样本没有精确重复 URL，新增 URL 缓存本身无法消除两次不同地址的 `ask` 请求。

现有 [search-general](../../../resources/skills/search-general/SKILL.md) 的工作流从搜索发现来源开始。本例只激活了 seecode，没有激活 search-general，因此不能把本次搜索次数归因于该 skill 的指令；但未来调整时应区分「用户已给明确 URL」和「需要发现来源」：前者先读指定来源，后者先搜索，仅在存在证据缺口时扩展。收口依据应包含已回答的问题、仍缺的证据和下一次调用的预期增量，避免为遵循统一流程再增加一次没有必要的来源发现。

技能激活与读取是否合并为一次调用，需要权衡工具协议、UI 激活状态、正文加载时机和缓存稳定性。本例只有一次激活和一次入口文档读取，优先级低于失败恢复。不会因为 pi 直接读文件，就推导出 ati 必须删除显式激活状态。

视觉检查应与任务质量要求匹配。用户要求可交付图形时，布局和视觉验收有价值；可改成针对重叠、裁切和关键连线的短任务，减少完整 OCR 式回传。但本次 44.5 秒尚未拆开视觉模型等待与输出生成，不能承诺缩短提示就能节省相同比例时间。也不建议直接关闭视觉检查来换取更低耗时。

同样不建议全局调低 Medium 思考等级、设固定工具调用上限，或降低网页就绪保障。这些动作会改变任务能力或证据质量，本次不足以支持统一默认值变更。

### 展示失败不是“PNG 坏了”：调用参数已有脱敏占位符

对照持久化消息与 BaseAdapter 流式原始工具参数：

- 第一张成功调用：`file: "diagrams/ponte-channels.png"`。
- 第二张图的三次失败调用：**`file: "[REDACTED]"`**。
- 导出结果和 `file` 命令确认真实第二张 PNG 存在且为 1364×1088；检查真实文件并不会修复占位符参数。
- 由于流式模型输出中已出现该占位符，这不是仅在 UI/持久化展示时被隐藏，重复提交的输入本身就有问题。

当前 [ContextRequest](../../../src/main/agent/runtime/context/ContextRequest.ts) 在 assistant 工具调用回放中对 `image_analyze` 与 `image_show` 的 `file/files`、URL 和 raw_data 都替换成 `[REDACTED]`，现有测试也明确覆盖这一行为。
这与本次模型重新生成占位符形成了强线索：图像二进制/签名地址的保护边界，可能连同可恢复的本地资源引用一起抹掉。
完整因果仍需出站请求快照或隔离回归确认，不能据此把所有图片脱敏直接取消。

此外 [ImageToolsProcessor](../../../src/main/tools/image/ImageToolsProcessor.ts) 将展示异常统一转成通用 `success:false/message`，没有指出占位符属于输入错误，也没有共享 `ToolFailure` 恢复信息。
模型于是把“输入没有修正”误当成“工具抖动”，连续重试后才交付路径。
