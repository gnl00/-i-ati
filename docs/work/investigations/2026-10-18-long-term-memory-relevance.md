## 范围与状态

本文件记录待讨论方案，运行逻辑尚未修改。近期活动最多三条、紧凑 awake 快照等改动已完成，
见 [ADR-0048](../../decisions/0048-bounded-awake-activity-context.md) 和
[首轮上下文优化记录](2026-10-18-first-turn-context-optimization.md)。

长期记忆分三个阶段，每个阶段可独立交付：

| 阶段 | 目标 | 当前状态 |
| --- | --- | --- |
| 阈值和跨聊天召回 | 低相关候选不进入上下文，新聊天能召回其他聊天中的相关记忆 | 本轮讨论重点，未实施 |
| 作用域与常驻 | 区分全局偏好、项目规则和主题事实，分开表达重要性与常驻意图 | 后续讨论 |
| 超长记忆 | 保留完整约束，避免静默截断；评估原子事实拆分与完整内容访问 | 后续讨论 |

第一阶段保持固定注入候选规则、记忆原文、存储 schema、embedding 模型、工具名称和请求注入位置。
不自动重分类旧记录，不增加摘要或翻译模型请求，不新增检索工具。

## 当前证据

2026-10-18 对当前用户资料库做只读统计：147 条记忆，分布在 68 个聊天中。
28 条满足固定候选条件，全部 147 条都没有显式 scope 元数据；4 条原文超过 720 字符，
有 2 个多余的完全相同原文副本。数字是本次快照，不作为固定配置或测试阈值。

固定注入条件为 high importance 且 category 属于 preference、workflow、style、constraint、project，
按时间取最新 3 条。当前三条候选都属于 constraint，主题涉及技能与工具、定时消息投递、请求诊断。
这些主题只用于说明重要性与通用性的区别，不能仅根据标签自动判定其适用范围。

相关记忆有以下实现缺口：

- Awake 的 raw query 和 contextual query 都传当前 chatId，形成硬过滤。新聊天没有本聊天记忆时，
  无法从这两路获得其他聊天的相关候选；固定注入仍来自全库，但只有三条。
- MemoryService 声明了 threshold 参数，却没有读取或执行它，实际直接返回 topK 结果。
- 工具处理器使用 `args.threshold || 0.6`，合法的 0 会被替换为默认值。
- Awake 当前排序最多叠加 0.25 重要性、0.08 分类和 0.04 时效加分。恢复阈值时应先按原始相似度
  判定资格，再排序，防止低相关条目靠元数据加分进入结果。
- 现有 [工具测试](../../../src/main/tools/memory/__tests__/MemoryToolsProcessor.test.ts) 的 MemoryService mock
  自己做了阈值过滤。这能验证工具转发与返回，却不能证明真实服务已过滤。

当前 [实现说明](../../data/memory-implementation.md) 记录参数默认值和数据所有权。
本讨论不把传入参数等同于底层已经执行的行为。

## 第一阶段建议

### 阈值作为服务层统一契约

在 MemoryService 中统一处理入口参数，工具、Awake 和 IPC 使用同一过滤逻辑：

- threshold 缺省为 0.6，合法范围为 0 到 1，包含边界；显式 0 保留。
- 资格条件为有限的原始 cosine similarity 大于等于 threshold，先过滤再排序。
  threshold=0 表示保留非负相似度，不表示允许负相似度或无效向量结果。
- topK 缺省为 5，范围为 1 到 10 的整数，作为返回上限；结果不足时允许少于 topK，甚至为空。
  非法值返回清楚的参数错误，工具继续使用现有结构化失败路径。
- 显式 chatId 继续是硬过滤，保留工具“只搜索这个聊天”的参数语义。
- 保留 excludeIds 和 timeRange；资格过滤后重新生成连续 rank。
- 工具处理器保留缺省与 0 的区别，不自行绕过阈值。共享 schema 补齐边界约束和说明。

该阈值只作用于相关检索支路。现有三条固定注入记忆继续保留，不因低于检索阈值消失；
固定注入是否适用于所有任务，属于下一阶段的作用域与常驻讨论。

当前 SQL 按 cosine distance 升序取 topK。如果资格只依赖同一距离，随后过滤是等价的，
不必为了过滤迁移向量表或更换索引。候选扩容只用于 Awake 后续的偏好排序。

0.6 沿用已有契约，属于首版控制值，尚无标注集证明它是当前本地模型的最佳准确率阈值。
未命中时不自动降低阈值，也不把近似分数描述为正确概率。

### 跨聊天召回复用现有查询

Awake 继续使用 raw query 和 contextual query 两路，移除它们默认携带的 chatId 硬过滤。
每路从当前用户资料库最多取 10 个候选，合并后按 memory id 去重，保留较高的原始相似度。
最终仍最多输出 5 条相关记忆，固定候选最多 3 条的逻辑保持原样，合并时继续去重。

这只改变 Awake 的默认召回范围。模型显式调用 memory_retrieval 时，chatId 的硬过滤契约保持原样。
跨聊天范围仍是同一应用用户资料库，沿用工具省略 chatId 时已经存在的全库检索能力。
不同项目的事实适用性仍有风险，第一阶段的相关性过滤不能替代下一阶段的作用域设计。

两路查询调用次数保持不变，候选池从每路 5 条扩大到最多 10 条。
不再追加当前聊天、全库各两路的四查询组合，避免重复 embedding 工作。

### 当前聊天作为小幅偏好

建议的首版排序为原始相似度加当前聊天 0.03 偏好；该常数需要固定样例校验。
重要性、类别和时效不再叠加当前幅度的分数，可作为同分时的稳定排序条件。
同分最终用时间与 id 确保顺序稳定，原始相似度继续单独保留。

| 相关支路候选 | 相似度 | 阈值资格 | 首版排序分 |
| --- | ---: | --- | ---: |
| 本聊天，重要性 high | 0.42 | 不合格 | 不参与 |
| 本聊天 | 0.65 | 合格 | 0.68 |
| 其他聊天 | 0.90 | 合格 | 0.90 |
| 本聊天 | 0.80 | 合格 | 0.83 |
| 其他聊天 | 0.82 | 合格 | 0.82 |

因此明显更相关的跨聊天结果能排在前面，分数接近时倾向当前工作。
候选池有界，当前聊天结果如果原本位于全库第 11 名以后，不保证被召回；本阶段不追求穷尽历史。

### 无主题与低质量 query

`yo` 之类缺少主题的首轮请求，相关记忆支路应直接为空，固定注入偏好仍保留。
通用问候、自动生成的 NewChat 名称或 workspace 路径不能单独构成可靠主题；
“继续”仍结合真实 work context、压缩摘要和已有主题标题。
复用现有活动主题判断的输入与原则，避免两套不同的问候词规则。

当前记忆向量来自 context_en，工具要求英文 query，Awake 却可能直接使用中文 raw query。
因此验证必须包含中文和对应英文问法。若恢复阈值后中文召回明显下降，应单独调查 query 与向量模型
的匹配，不能通过静默降低阈值、重新嵌入全库或自动增加翻译模型掩盖。

## 第一阶段验证与交付边界

测试必须触达真实 MemoryService 的过滤路径，包含实际 SQL 或向量扩展集成，不能只使用自己过滤的 mock。

| 用例 | 预期 |
| --- | --- |
| 0.59、0.60、0.61，threshold=0.6 | 只保留后两条 |
| 显式 threshold=0，包含负数与非负分数 | 保留非负分数，0 不被工具默认值覆盖 |
| NaN、越界阈值、非整数或越界 topK | 明确参数错误 |
| 合格项不足或为零 | 返回较少项或空结果，不回填低相关候选 |
| 显式 chatId、excludeIds、timeRange | 所有现有过滤仍有效 |
| 新聊天查询其他聊天已有主题 | 能召回相关记忆 |
| 较弱本聊天项与较强跨聊天项 | 按上述资格和排序规则选择 |
| 两路查询命中同一 id | 合并一次，保留较高原始相似度 |
| 无主题、继续、中文与英文主题 | 无主题跳过检索，任务连续性保留，语言差异有记录 |
| 某路相关记忆检索失败 | 固定偏好及其他成功支路仍可用，不清空整份记忆快照 |

验证命令以实施后的新增服务测试为准，并至少运行现有 memory 工具、Awake、请求准备测试，
Node/web typecheck、变更文件 lint、Main 架构检查和全仓 coverage。
使用固定正例、反例和中英文问法记录候选、原始分数、过滤结果、最终选择和未命中比例；
日志只输出必要的内部诊断，不重复写入私人记忆原文。没有准确率实测时，不宣称召回质量提升百分比。

实施前需明确确认 0.6 阈值、每路 10 个候选、最终 5 条相关记忆及 0.03 当前聊天偏好。
这些是推荐起点。第一阶段不做数据库迁移，回滚运行代码即可恢复旧查询与投影；
部署、Git 提交和付费模型验收均不包含在本讨论中。
